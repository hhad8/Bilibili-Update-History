# Bilibili Fawkes Update Archive

本项目旨在整理并归档哔哩哔哩官方 Android 客户端在本地生成的版本升级响应缓存文件。

这些文件是客户端检查更新时保存的响应数据，通常包含版本号、更新说明、官方下载链接、文件大小、MD5 和发布时间等信息。可以用来查找官方的历史更新日志、旧版本安装包的官方下载链接等信息。

> 本仓库为个人整理的资料归档，**仅用于学习和测试，与哔哩哔哩官方无关。** 仓库本身未提供或重新分发 APK 安装包，仅收录更新接口相关的响应数据。

---

## 关于更新接口

公开资料记录的 Fawkes 更新检查接口为：

```text
https://app.bilibili.com/x/v2/version/fawkes/upgrade
```

接口说明可参考 [bilibili-API-collect 的版本接口文档](https://github.com/pskdje/bilibili-API-collect/blob/main/docs/APP_widget/ver.md)。

当哔哩哔哩 Android 客户端启动并触发版本检查时，会向相关接口发送请求。若服务端判定有新版本需要提示升级时，返回的 JSON 会被客户端直接持久化保存在本地私有目录下，文件通常以当前目标版本的 `version_code` 命名，扩展名为 `.apk.infofawkes`（例如 `8300100.apk.infofawkes`）。

这些文件是**证明特定历史构建存在的最直接官方证据**，包含官方服务器的原始发布时间戳、下载直链及校验哈希。

## 文件命名与内容

文件名通常是数字版本代码加 `.apk.infofawkes`，例如：`8300100.apk.infofawkes` `9010300.apk.infofawkes` 等。

文件内容通常是 JSON。常见字段包括：

| 字段 | 含义                   |
| ------ | ------------------------ |
| `version`     | 响应中给出的版本名称   |
| `version_code`     | 响应中给出的版本代码   |
| `url`     | 安装包下载地址         |
| `size`     | 安装包大小，单位为字节 |
| `md5`     | 安装包 MD5             |
| `ptime`     | 发布时间 Unix 时间戳   |
| `content`     | 更新说明               |
| `title`     | 更新提示标题           |

文件名中的数字通常与 JSON 的 `version_code` 对应。**相同的版本名称可能对应不同的** **`version_code`** **、构建号或下载链接**，因此如需提交请保留原始文件名和响应内容，不要根据 `version` 字段重命名或合并记录。

例如，8.30.0 的记录可能出现不同的版本代码和下载构建号。构建号暂时无法仅由版本名称或 `version_code` 推算。

## 缓存文件存放路径

不同 Android 系统版本及客户端变体的缓存存储路径如下：

### 1. 国内版（包名：`tv.danmaku.bili`）

- **较新 Android 版本（受沙盒及权限限制，通常需要 Root 或应用调试权限）：**

  ```text
  /data/data/tv.danmaku.bili/files/update/
  ```
- **老版本 Android / 外部私有目录：**

  ```text
  /storage/emulated/0/Android/data/tv.danmaku.bili/files/update/
  ```

### 2. Play 版（包名：`com.bilibili.app.in`）

- **内部私有存储：**

  ```text
  /data/data/com.bilibili.app.in/files/update/
  ```
- **外部私有存储：**

  ```text
  /storage/emulated/0/Android/data/com.bilibili.app.in/files/update/
  ```

## 技术细节与发现

### 版本分发特征

通过对收集到的历史样本进行交叉比对，归纳出以下分发特征：

1. **URL 构建标识独立于版本号：** 
   官方 CDN 链接结构为：

   ```text
   https://dl.hdslb.com/mobile/pack/<arch>/<build_id>/iBiliPlayer-<flavor>-<version>-b<build_id>.apk
   ```

   中间的目录号与文件名后缀 `b<build_id>` 一致。这一构建 ID 属于服务器独立的流水线编号，目前暂未发现其他规律，只知道会随版本更新递增的特性。
2. **同一版本存在多构建（Gray / Iteration）：** 
   同一个 `versionName` 可能对应多个不同的构建号与发布阶段。例如：

   - `8.30.0` (8300100) 对应构建号 `17403134`（大小 159,044,745）
   - `8.30.0` (8300300) 对应构建号 `17448734`（大小 160,343,749）
3. **架构与包名规则变迁（受提取设备影响）：**

   - **架构分发：**  目前收集到的现有样本中，7.64.0 之前均为 32 位包，而 7.64.0 之后均为 64 位包（CDN 路径使用 `android64`）。**可能是因为早期样本提取自配置较低的老旧设备，升级接口根据设备上报的 ABI 下发了 32 位版本**，并非意味着当时官方不存在 64 位安装包。真实的分发策略仍需更多不同设备的样本共同佐证。
   - **命名模板变化：**  早期版本文件名多使用 `iBiliPlayer-apinkRelease-...`，在后续演变中逐步精简为 `iBiliPlayer-release-...`。

### 客户端缓存生成特性

根据目前收集到的文件观察，国内版客户端会在更新目录中保留历史响应文件；某个版本的记录通常需要客户端在相应期间请求到该版本的更新响应后才会生成。

因此，如果某个版本期间没有启动客户端或没有触发相应更新检查，就可能没有该版本的缓存文件。**缺少记录不代表该版本没有发布。**

另外目前仅存有一份 Play 版 `3.18.2` 的记录。曾观察到 Play 版目录可能只保留最新一次更新响应，但这一点尚未充分验证，推测 Play 版历史记录可能会自动覆盖/清理旧版本相关记录。

## 参与贡献（提交样本）

由于缓存按需生成的特性，仓库中收录的版本**并不一定是连续、完整的。** 欢迎提交 PR。

并且由于每个用户的设备更新频次、网络环境和灰度命中情况不同，**也不保证涵盖同一版本的所有构建或变体，所以即使仓库中已经收录了某个版本，依然强烈欢迎提交你设备里的文件！**

我们可能会从中发现：

- 相同的版本号，但属于更早/更晚的灰度批次（不同 MD5 / 构建号）；
- 相同版本针对 32 位与 64 位设备的不同下发链接；
- 不同的升级文案或策略标签（`cycle` / `policy`）。

### 提取方法：

1. 若设备已 Root，直接使用文件管理器（如 MT 管理器、Root Explorer）进入：
   `/data/data/tv.danmaku.bili/files/update/`
2. 未 Root 设备可检查外部存储目录：
   `/storage/emulated/0/Android/data/tv.danmaku.bili/files/update/`
3. 使用 ADB 备份或提取（需开启调试）：

   ```bash
   adb shell "su -c 'ls -l /data/data/tv.danmaku.bili/files/update/'"
   ```

### 提交前请：

1. 尽量保留文件原名和原始 JSON 内容，不要手动更改文件中的内容。
2. 尽量在提交说明中注明客户端类型（国内版或 Play 版）、版本目录，以及大致收集时间。
3. 如果同名文件内容不同，请不要直接覆盖。可将不同副本另存为带日期的文件名，并在提交中解释有哪些区别。

### 提交方式：

- **Pull Request：**  按照大版本放入对应目录提交 PR。
- **Issue：**  直接在 Issue 中上传 `.apk.infofawkes` 文件或粘贴完整 JSON 内容，可以注明文件来源设备的基本信息（如 32/64 位、机型等）。
